## 0. 给实施者的硬约束（提示词）

后续改代码、写方案、做接入时，先遵守本节，再看具体阶段任务。本节的效力高于「把界面做完整」或「把通用 Agent 做聪明」。

### 0.A 什么是壁垒，什么必须可替换

- **壁垒（必须建设、必须留在内网）：** 本地参考库、版本化知识库、鉴定规则、证据服务、计算插件（Workflow 1–6 及后续标准流程）、专家审核记录，以及在量化本地模型上完成四类窄任务的能力。
- **可替换层（维持闭环即可，禁止加深耦合）：** Open WebUI 或其他前端、Claude Agent SDK、DeepSeek Harness、云端大模型供应商。它们只是把用户意图送进本系统的动作契约。
- 不得把领域规则、权限、方案编译、Snakemake 启动或报告模板写进某一家 Harness 的 prompt / skill 文件里作为唯一实现。
- 不得以「先做完通用 Agent 再补知识」为理由推迟本地库和知识发布。知识与参考库与阶段 1 业务闭环**并行**。

### 0.B 产业化与本地化

- 默认 **local_only**。没有管理员策略 + 用户确认，不得把样本、路径、报告或对话发到云端。
- 交付物按资产包思维管理：参考库包、知识包、规则包、计算插件包、本地模型包、业务库。每一类可单独发版、单独校验、单独回滚。
- 现场更新路径固定为：导入 → 校验清单/哈希 → 回归 → 切换默认快照。正在运行的任务和已发布报告继续使用旧快照。
- 原始 FASTQ 不修改、不搬动。计算产物只写入 run root。

### 0.C 模型与执行边界

- 模型只产生 `respond` / `clarify` / `propose_patch` / 研判草稿；确定性服务负责配对、编译、参数校验、路由、执行和报告渲染。
- 本地模型首期只做四类任务：意图识别与追问、受控参数建议、带引用的知识问答、候选证据说明。不要求自主多轮 MCP 工具调用。
- 失败时停在明确状态并转表单或专家，不自动回云端，不无限修 JSON。
- 强化学习调度、未校准总概率、自动改写线上规则、自主无限派生 Agent：**不做**。

### 0.D 交互主路径（必须可走通，且尽量不依赖模型）

`选择或上传文件 → 确定性自动配对与预检 → 用户确认样本关系 → 选择目标与标准/紧急模式 → 确定性编译方案 → 用户确认 → 排队执行 → 快报/完整报告 → 多证据研判 → 专家审核`。

纯结构化路径在模型不可用时仍能规划、确认并执行分析。

## 1. 执行约定与基线

目标是交付**可私有化、可迭代更新**的病毒鉴定与专家研判系统：计算产线产出可复算事实，本地知识解释事实，专家审核形成结论，本地小模型只在窄任务上辅助。业务闭环按 **1A → 1E** 推进；**知识与本地库从阶段 0 即开始**，不阻塞在 1A–1E 全部完成之后。阶段 5 专项能力按条件接入。

每个小任务以可单独验证和回退的变更交付。开始下一阶段前记录上一阶段的代码版本、验收结果和未开放能力；每次只启用通过验证的能力。生物学阈值、模型质量门槛和性能预算先由阶段 0 建立基线，再由相应领域负责人确认，不能把本文中的工程方案当作已验证的生物学结论。

### 1.2 全阶段保持的边界

- 浏览器经 WebUI 后端访问业务数据；后端负责用户身份、项目权限和业务写入。BioAgent 不直接读取或写入 WebUI 数据库。
- 模型产生建议与解释，确定性服务负责方案编译、数值计算、参数及引用校验。执行和补算由明确的确认动作触发。
- 原始 FASTQ 不修改、不搬动。计算及生信测试产物只写入 run root；测试上传使用专用测试 run 内的隔离目录，不能污染真实 dataset。
- 远端调用固定 `ssh -o ClearAllForwardings=yes`；沿用 Home Pixi Python／Snakemake／SeqKit 与私有 tmux，停止本机服务不终止远端分析。
- 不读取或输出私有密钥；配置变更只维护 tracked `.env.example`，实际环境文件保持忽略提交。
- 知识、参考库、方案和报告分别版本化。历史报告不能因索引重建、模型切换或规则更新而被静默改写。
- 本地默认，云端显式启用。资料内容作为检索数据，不能改变宿主权限、工具白名单或执行规则。
- 编排运行时（Claude Agent SDK / DeepSeek Harness / 本地 OpenAI 兼容服务）必须位于 provider 适配器之后。新增对话能力时先改契约和宿主服务，再改某一家 SDK。
- 计算节点只暴露已注册 capability；Agent 节点不在计算服务器上直接持有参考库或写 Snakefile。

### 1.4 知识库与本地数据库建设策略

#### 知识库（应用侧，可断网）

目标形态：不可变资料包 + SQLite 元数据/关系表 + FTS5。不先上图数据库或独立向量服务。

1. **收什么：** ICTV 官方标准与科级阈值、标志基因与别名、本项目 W1–W6 技能卡、已接入工具的只读说明、可合法获取的方法学文献与摘录。
2. **怎么进：** 导入 → 登记 DOI/URL/许可/内容哈希 → 结构化为 Source / Passage / Entity / Relation → 专家审核 → 构建索引 → 回归检索集 → 发布 KnowledgeRelease。
3. **怎么用：** 检索按任务、类群、知识版本过滤；返回 citation_id、locator、原文片段。只有发布且可定位的 ID 才能进入对话或研判。`ConversationAction.validate_action` 不得再无条件清空 citations，也不得信任模型自填的 ID。
4. **怎么更新：** 已发布资料原地不可改。纠错和新 ICTV 版本发新 release。历史报告钉住旧 snapshot。发布失败保留上一快照；无快照时暂停知识问答，保留确定性分析。
5. **安全：** 资料中的指令性内容不得提升工具权限或外发数据。中文词项统一预处理，英文基因名/taxon ID 精确匹配。向量检索只在固定集证明增益后才加。

#### 本地参考库（计算侧，离线包）

1. **管什么：** NT、NR、Kraken2、CheckV、rRNA、宿主/BOLD、各 workflow 专用库。
2. **目录字段：** 库 ID、来源、下载或构建日期、构建命令、工具兼容版本、文件清单、哈希、大小、验证记录。版本未知一律标 `unknown`，禁止用目录名猜测。
3. **切换：** 计算插件声明所需库 ID。执行前核清单与完整性。库变更禁止自动续跑中断任务，必须新方案/新 run。
4. **现场更新：** 离线介质或内网镜像导入 → 校验 → 小样本回归 → 切换默认。Agent 节点不复制整库。

#### 工具库如何支撑报告

工具/capability 注册表是编译器和报告的同一来源：输入输出类型、参数、参考库依赖、解析器、验证状态。解析器把 artifact 变成候选级证据（身份、完整性、同一性、覆盖、对照状态），规则包标记矛盾与缺失，知识包提供适用条文。模型不得另写一套工具能力说明。

### 1.5 计算插件与编排解耦

- Workflow 1–6（及以后基因组补齐等）以 `capability_id + adapter 版本 + 参考库快照` 注册。新增流程 = 新适配器 + 契约测试 + 至少一次真实或 dry-run 验收，而不是在 Agent 里新写 Bash。
- 计算节点经 SSH worker 执行；MCP 用于外部知识/专项服务的发现与调用，不要求把 Snakemake 改造成 MCP 才能跑。
- 若接入 DeepSeek Harness 或其他编排器：只替换 provider 与会话传输，不替换 catalog / compiler / runner / 知识模块。

### 1.6 本地模型与微调（约束，不是立即训练）

- 先有动作契约、知识快照、证据包，再选量化模型和推理后端。
- 微调数据只来自：冻结任务集、专家审核修订、合法的「证据包 → 结构化说明」对。不把原始测序、密钥、未审核聊天当训练数据。
- 发布新模型包与发布知识包相同：评测 → 影子运行 → 按能力切换。切回不改写历史报告。

## 2. 阶段 0：建立现状与评测基线

**目标：**形成可以重复核对的能力、资源、参考库和评测清单。**前置条件：**无；只读盘点与受控测试分别进行。**主要负责人：**工程维护者联合生信维护者、领域专家。

### 0.1 盘点已接入能力与参考库

- [ ] 从 `agent/workflow_catalog.py`、`pipeline_spec.py`、`workflow_adapters.py` 生成目标 → stage → artifact → 工具／参考库映射，标记每个入口的验证状态。将该表作为计算插件目录的第一版，而不是内部备忘。
- [ ] 通过 Cyclone 只读检查 workflow 配置及实际工具入口，记录 NT、NR、Kraken2、CheckV、rRNA 和 workflow 专用库的路径、来源、版本、索引格式、构建信息、大小和可读性；不在盘点时批量搬库或重建索引。
- [ ] 区分源码配置、run-local 覆写及实际执行命令。记录现有参考库缺少版本证明的情况，以 `unknown` 明示，不从目录名猜测。
- [ ] 记录 CPU、内存、磁盘及可用推理硬件；执行代表任务后再给资源预算。当前 `/data` 的吞吐限制与 Home Pixi 工具位置进入部署基线。

**接口与产物：**先使用一份版本化能力／参考库清单，无须立即增加服务。清单包含能力 ID、输入类型、工具版本、参考库 ID、验证记录及限制；后续阶段 1 将其中必要字段接入方案快照。

### 0.2 冻结验证数据和指标口径

- [ ] 建立小规模、可重复的解析与编译 fixtures，以及单独的真实数据验收集；数据集记录许可、来源、预期用途和专家标注。
- [ ] 覆盖已知病毒、低丰度、混合样本、分节段、局部高同源低覆盖、阈值附近、对照缺失、质量异常和无法分类候选。没有可靠真值的案例只评估异常提示及补证行为。
- [ ] 对已提供的 FASTQ 先做预检和 DAG dry-run；真实计算作为单独验收任务登记 run，记录工具／参考库／方案版本，不覆盖原始文件。
- [ ] 扩展 `agent/benchmarks/conversation_actions.json`：加入中文改参、歧义目标、非法动作、无依据引用、空知识、超时和云端禁用案例，区分纯契约测试与真实模型评测。
- [ ] 冻结评测划分。知识编写和提示词调试使用开发集，模型迁移比较使用留出集；按候选或同源群分组，避免近重复样本横跨评测划分。
- [ ] 分别定义数值正确性、分类与候选发现质量、知识召回与引用适用性、模型任务完成率、审核成本和运行耗时；不将它们合并为一个不可解释的分数。

**验收：**每个开放能力能回答“输入是什么、依据哪个工具／库版本、输出如何核对、验证到什么程度”；代表样本产物可定位，当前 MiniMax-M3 基线可重复运行。

**回退与退出：**只读盘点没有运行影响。未验证能力标为不可用或限测试，不用已完成的文档条目替代运行证据。

## 3. 阶段 1：补齐业务与执行闭环

**目标：**实现真实项目归属、完整数据入口及可信的执行生命周期。**前置条件：**阶段 0 的能力清单和基础验证用例就绪。按 1A → 1B → 1C → 1D → 1E 交付，每个子阶段独立验收。

### 1A 项目、成员与会话归属

- [ ] 在 WebUI 后端增加 Project／ProjectMember；管理员创建项目、设置优先级和成员权限。权限区分查看、分析和审核，成员可拥有多个权限；平台管理员负责成员管理。
- [ ] 会话绑定一个项目，数据集、方案、执行和报告沿该关系授权；保留现有 user_id／chat_id 字段记录创建者与上下文。
- [ ] 后端校验列表、单对象、下载、执行和报告访问，跨项目对象 ID 不得绕过授权；远端文件列表只暴露已授权项目的逻辑根。
- [ ] Dashboard 使用真实项目及状态聚合，移除对应示例数组。项目内展示多个分析会话，计算完成与待审核数量分别统计。
- [ ] 迁移历史会话时按原用户创建“历史分析”项目，由管理员后续分配；不将旧会话自动公开给新增项目成员。原用户访问范围保持可追溯。

**代码落点：**`open-webui/backend/open_webui/models/analysis_*.py`、`routers/analysis.py` 与迁移目录；Dashboard、AnalysisPage 及 analysis API 客户端。

**最小接口变化：**在现有 `/api/v1/analysis` 下新增 projects／members 资源；数据集和会话携带 project_id；执行由后端从已授权对象派生项目身份，不能信任模型或浏览器自行声明的优先级。Agent 编译与执行接口仅接收后端验证后的上下文。

**验收：**两个用户分属不同项目时，列表、详情、文件路径、报告下载和执行均隔离；拥有多个项目的用户能切换；迁移后的旧会话仍可由原用户访问。

### 1B 上传、样本元信息与数据冻结

- [ ] 增加上传会话：服务端生成上传 ID 和目标位置，记录项目、文件名、期望大小、已收偏移及状态。分块通过后端受限流式传到远端暂存区，不在应用内存缓存整份 FASTQ。
- [ ] 首期分块按偏移顺序接收；重复分块只有内容一致才幂等接受，错误偏移明确拒绝。断线后按服务端偏移继续；限制单次块大小和项目配额。
- [ ] 完成时校验总大小和内容摘要，原子提交到项目数据根；失败或未完成上传不进入 dataset。提交后使用现有 resolve／preflight／fingerprints 入口，不引入第二套数据校验。
- [ ] 提供终止上传和清理过期暂存的显式管理动作；清理只处理本服务登记的暂存对象，不扫描删除原始数据。
- [ ] 保存 sample_id、测序 run／batch、宿主背景、样本类型、可选表型与对照关联；对照缺失是信息状态。技术重复与生物学样本合并必须有明确记录。
- [ ] 增加元信息修订；会影响计算的变化产生新数据集／方案版本，纯报告背景修订形成报告输入版本，不修改历史快照。

**接口变化：**新增 uploads 的创建、状态、分块、完成和终止接口；扩展 dataset 元信息。浏览器只提交文件内容和逻辑标识，远端路径由服务端生成。typed artifact 继续按 catalog 的完整文件束准入。

**验收：**分块断线续传、重复提交、摘要不符、超额、配对错误、越界路径、symlink 更换和远端暂不可用均有明确结果；上传完成前不能执行分析。暂时不能验证指纹返回 retryable 503，数据集原状态不变。

### 1C 受控参数与执行快照

- [ ] 工具目录增加经验证的参数 schema 和具名预设；首期为已有 fastp 配置建立标准／宽松预设，具体数值由生信维护者结合阶段 0 用例审核。
- [ ] 扩展 ProposedPatch 仅允许引用 preset_id 或白名单字段，所有提议经过同一个参数验证器和确定性编译器。用户看到展开后的数值差异、受影响步骤与资源估算。
- [ ] `rrna_filter` 保持去 rRNA 语义。宿主序列去除作为单独的 `host_filter` 能力，只有宿主参考库、输出 artifact、依赖变体及验证案例齐全才开放；未接通时对“不做宿主去除”明确说明现有方案内容。
- [ ] 仅在 DAG 存在经过验证的旁路时允许省略步骤；不能删除必需步骤后伪造 clean reads 类型。新类型／依赖变体同步 catalog、compiler、adapter、UI 与解析器。
- [ ] 方案冻结展开后的参数、工具／workflow 版本、参考库快照与规则版本；执行前核对。大型库的校验基于发布时生成的不可变清单及运行时完整性状态。
- [ ] 对旧方案不补写未知版本。旧记录可读，新执行要求重新编译并确认完整快照。

**代码落点：**`conversation_contract.py`、`workflow_catalog.py`、`pipeline_spec.py`、`deterministic_planner.py`、`workflow_adapters.py`；后端方案／proposal 模型与前端确认卡。

**接口变化：**扩展 options 与 ProposedPatch；新增 reference_snapshot 标识及展开的参数快照。对执行 spec 的不兼容变化升级版本并拒绝以旧 spec 启动新任务，不维护无需求的执行兼容层。

**验收：**合法预设可通过自然语言建议和表单得到同一方案；非法参数、未发布预设、遗漏依赖及确认后数据变更全部被拦截；用户拒绝提议不产生新执行。

### 1D 智能模式的阶段交付

- [ ] 修改 `adaptive_routing.py`、`analysis_runner.py`：auto 在初筛后继续已确认完整目标，不再因门槛通过把剩余步骤设为 skipped。
- [ ] 保留初筛比例 5% 作为可复现的现有基线，记录采样种子、实际配对数、质控／去 rRNA 结果和所用 Kraken2 库。门槛只用于初筛信号提示，其生物学适用性仍需验证。
- [ ] 初筛数值复核后发布不可变 preliminary 报告；增加报告列表／版本和可用性字段，与 execution status 分离，运行中也可下载快报。
- [ ] 完整流程资源不足时进入 waiting_resources，保留快报与原目标；资源准入后继续。输入／工具故障停止并标明原因，不能伪装为未检出或自动删减目标。
- [ ] emergency 首期明确为现有“5% 抽样＋质控＋去 rRNA＋Kraken2”快检；确认页面只承诺该范围。成对 reads 不可用时拒绝紧急模式，智能模式改用标准前必须在确认页面说明。
- [ ] 标准模式依旧执行目标依赖闭包；初筛使用的子集产物不能充当后续全量 clean reads。保留完整输入重新进入目标流程。

**接口变化：**routing policy 的版本与语义更新；run snapshot 增加独立 reports 列表，至少区分快报、完整分析、研判及其 revision／scope／availability。后端报告查询从“单一终态报告”扩展到指定版本，沿用证据复核和模板渲染。

**验收：**高信号、低信号、多样本混合结果均在 auto 中继续用户目标；完整流程失败时快报仍可下载并说明范围；旧报告保持原路由及解释，不在页面重读时更改结论。

### 1E 显式队列与受控恢复

- [ ] 使用远端持久化队列和单一调度者决定任务顺序；保留 flock 作为并发互斥的最终约束，不能继续让多个 supervisor 竞争锁来决定业务排序。
- [ ] 默认一个重型任务准入。排序依次为管理员项目优先级、项目内紧急级、入队时间；设置可配置的最长等待提升规则。工程初始默认等待 24 小时的任务按入队时间优先选取，仅作用于符合资源条件的任务，后续根据实际队列调整并记录策略版本。
- [ ] 优先级修改只作用于尚未启动的任务；正在运行的任务不抢占。在阶段边界检查 CPU、内存与磁盘可用性，等待资源的任务释放准入资格，允许其他符合条件的任务运行。
- [ ] 队列持久化项目、run、attempt、优先级、排队时间、状态和等待原因。以事务／唯一约束保证多个请求、控制进程重启和网络重试不会重复启动同一 attempt。
- [ ] 本机停机不终止远端调度与运行；远端调度者恢复时先 reconciliation，再选择待执行任务。显示连接时间和缓存状态。
- [ ] 新增显式恢复入口，仅允许 interrupted 等可恢复状态。核对相同输入、方案、工具、参考库和 worker 执行条件，以及阶段输出完整性；同一 run 下追加 attempt，保留旧日志与状态记录。
- [ ] 版本一致且完整的结果交由 Snakemake 复用，不完整产物由原规则重建。执行条件改变时新建方案／run，按 typed artifact 契约导入可复用结果；不自动重跑中断任务。

**代码落点：**`remote_worker.py`、`remote_client.py`、`deterministic_runtime.py`、`analysis_runner.py`、`resource_calibration.py`；WebUI 执行模型、snapshot 映射与状态 UI。

**接口变化：**增加受授权的队列优先级更新与恢复动作；start 使用原有执行唯一性并增加 attempt 身份；snapshot 增加 queue、attempt、waiting_reason、observed_at。业务后端负责授权，远端负责实际队列／进程事实。

**阶段 1 总体验收：**完成“项目 → 上传或选择 → 冻结数据 → 确认预设 → 排队 → 快报 → 完整结果”的真实闭环；故障测试覆盖 SSH 断开、control 重启、queued session 消失、running 进程消失、boot ID 变化、参数／参考库改变及重复恢复请求。

**迁移与回退：**数据库迁移前备份并演练。新队列只在旧队列清空或完成逐项登记后接管，不能同时运行两种调度者。回退应用前停止新任务准入、等待或登记在途任务；保留新版本数据，旧代码不强行读取不支持的 schema。路由回退不静默恢复 auto 的提前结束语义，可暂时只开放标准与明确范围的紧急模式。

## 4. 阶段 2：建立四类知识资产、本地库目录与引用闭环

**目标：**让现场断网也能检索少量可信知识，并让每份计算报告能绑定参考库版本。**前置条件：**阶段 0 的能力／参考库清单可用。不必等阶段 1 的上传与队列全部完成；无项目权限时先在受控内部项目中发布知识快照。

### 2.1 知识存储、整理与发布

- [ ] 在 agent 侧建立独立知识模块：不可变资料包＋SQLite 元数据、关系表和 FTS5 索引。先复用单进程部署，无须引入图数据库或独立向量服务。
- [ ] 建立 Source、Passage、Entity、Relation、KnowledgeRelease。关系至少记录 subject／predicate／object、来源片段、适用范围和版本；Source 记录 DOI／URL、内容哈希、许可、发布时间或采集时间、审核状态。
- [ ] 从 ICTV、工具官方文档、本项目流程说明和可合法获取的论文开始；不把未经审核的模型抽取直接发布为知识事实。全文不可得时只索引可用资料，并在引用中标明摘要或摘录范围。
- [ ] 技能卡保存 skill_id、version、任务类型、前置条件、工具／规则引用、预设、解释模板及验证案例；工具可执行能力继续以 catalog／adapter 为唯一依据，导出只读知识视图。
- [ ] 发布流程固定为导入、校验、专家审核、构建索引、回归验证、切换默认快照。已发布资料原地不可修改，纠错新建 release，保留旧快照供历史报告访问。
- [ ] 同步建立参考库发布目录（NT/NR/Kraken2/CheckV/rRNA 及 workflow 专用库）：清单、哈希、兼容工具版本、离线导入说明。执行 spec 只引用目录中的库 ID。
- [ ] 首期知识语料顺序：ICTV 科级标准 → 本项目技能卡（由 catalog 导出只读视图）→ 工具官方文档 → 可合法获取的方法学摘录。不把 TaxonAgent 在线查询当作本地知识库。

**知识图谱范围：**先覆盖类群名称与别名、标志基因、适用分类规则、来源片段、相关技能／工具。每条边有来源；不得将相似文本推测出的联系直接当作已证实生物学关系。

### 2.2 检索与引用可信边界

- [ ] 实现现有 `RetrievalAdapter.retrieve`，保留 query／corpora／limit，增加明确的 knowledge_release 与适用类群过滤。四类资产是知识组织方式，现有 Corpus 分类可按检索用途扩展，不要求硬凑成四个枚举。
- [ ] 精确匹配 taxon ID、别名和版本后，检索关系及原文片段；中文词项在导入和查询时按同一规则预处理，英文基因名和工具名保留精确查找。先用固定检索集验证，再决定是否增加向量召回。
- [ ] 检索排序分数只用于相关度。服务返回引用 ID、来源、版本、locator 和实际片段；只有审核发布且可解析定位的资料才能由服务标记可信。
- [ ] 修改 `ConversationAction.validate_action` 当前清空 citations 的逻辑：先建立服务端引用注册与解析，再允许模型返回本次检索结果中的 ID。未知、跨项目或来自不同快照的 ID 拒绝，不能仅相信模型填入的 quality。
- [ ] 记录提问、使用的检索快照、命中片段及最终 claim → citation 映射。咨询和方案提议引用通过后端现有 proposal／event 机制持久化。
- [ ] 空知识返回 KNOWLEDGE_INSUFFICIENT，服务不可用返回 RETRIEVAL_UNAVAILABLE；来源冲突同时返回并要求说明，不能仅选排名最高的一条当作确定事实。
- [ ] 对资料中的指令性内容做数据隔离；检索材料不能增加工具权限、改写项目范围或要求输出密钥。保留必要上下文以避免断章取义。

**代码落点：**`conversation_contract.py`、`taxonagent_adapter.py`、`runtime.py`、`conversation_context.py`；WebUI proposal、event 和引用展示。TaxonAgent 保持可选，不作为本地知识工作的前置依赖。

**最小接口变化：**Citation 增加 snapshot／source hash 和审核来源标识；RetrievalResult 保留原有错误语义并携带快照；增加内部 cite-resolve／verify 能力。先作为模块接口实现；WebUI 如需展示片段，经授权后端转发，不暴露知识文件系统路径。

**验收：**使用已知答案与空答案检索集，核对类群、版本、别名、中英文词项和原文定位；伪造引用、跨项目片段、失效定位、冲突规则、仅摘要来源及资料中的越权指令均不会被当成可靠结论。

**迁移与回退：**旧报告无文献引用时明确保持“未提供”，不自动补写。发布失败继续使用上一知识快照；没有可用快照时暂停知识问答，保留确定性分析。索引可以由资料包重建，历史引用解析不能依赖当前默认索引。

## 5. 阶段 3：候选级证据融合与专家审核

**目标：**将当前数值报告扩展为有计算来源、知识依据、冲突说明和审核状态的研判报告。**前置条件：**阶段 1 的报告版本／运行身份、阶段 2 的可信引用就绪。

### 3.1 标准化证据与规则服务

- [ ] 从现有结果解析器增量提取候选级数据，不重新编写一套独立数值计算。缺失字段显式保留 null／missing，不把 0 用作未提供值。
- [ ] CandidateEvidence 至少包含 dataset_revision、run_id、attempt_id、sample_id、candidate_id、metric、value、unit、definition、source_locator、source_hash、derivation、tool_version、reference_snapshot 和 source_group。
- [ ] 对同一性区分核酸／蛋白、query／subject、比对区间；对覆盖区分序列比对覆盖、参考基因组 breadth、测序 depth；对分母区分 reads／pairs、全量／抽样／过滤后。解析阶段完成单位校验。
- [ ] 建立规则包，输出适用范围、命中规则、支持项、反对项、冲突与缺失；来源组避免同一 reads 派生结果重复计票。首期不构造未经校准的总概率。
- [ ] 覆盖高同源低覆盖、样本关联错误、对照缺失、混合信号、分节段证据不足及阈值附近提示。EVE、污染、嵌合等提示必须基于实际可用指标；CheckV 结果按其适用范围使用。
- [ ] 分类规则引用对应类群、版本及来源。没有适用规则时记录“证据不足／待专家研判”，不采用跨类群统一百分比阈值。参见 [ICTV Code](https://ictv.global/about/code) 和 [CheckV 原始研究](https://www.nature.com/articles/s41587-020-00774-7)。

### 3.2 主 Agent 研判与交付核验

- [ ] 采用固定编排：证据标准化 → 规则检查 → 定向知识检索 → 主 Agent 说明 → 数值／引用校验 → 待审核报告。保留一个主 Agent，不新增融合 subagent。
- [ ] 研判任务按候选或有限候选组裁剪上下文，明确输入数值、规则结果、来源片段和可输出字段；允许分批执行，不要求模型同时记住全项目。
- [ ] Assessment 独立保存 taxonomy_assignment、support_level、supporting_evidence、opposing_evidence、conflicts、missing_evidence、citation_ids、limitations、next_actions、review_status，以及模型／提示模板／知识／规则版本。
- [ ] 支持程度使用充分支持、有限支持、证据不足、现有证据不支持当前归属；由审核规则允许的范围约束。冲突是独立维度，模型不得删除已命中的冲突和关键缺失项。
- [ ] 复用 `report_evidence.py` 的来源复算机制；新增字段有显式解析或派生公式，不能允许任意 eval。模型提交的证据 ID 和 citation ID 必须属于本次输入包。
- [ ] 校验数值、引用身份、定位和规则范围；将文献语义适用性列入专家清单。程序校验通过只表示结构和可追溯性通过，不等于证明生物学推断正确。
- [ ] 模型失败时保存结构化指标、规则结果和“未生成研判”状态，仍可交付已核验的计算报告。模型不生成可直接执行的 HTML，后端模板渲染并转义文本。

### 3.3 审核、修订与补算

- [ ] 增加审核权限和 ReviewEvent：报告 revision、审核人、决定、理由、引用证据、时间、被替代版本。决定包含认可、需补证和要求修订，不能覆盖原始模型输出或旧审核。
- [ ] 报告将计算状态、研判状态和审核状态分开展示。相互矛盾的审核决定保留完整记录，由有审核权限的用户明确选择形成新版本，不以最后写入悄然覆盖。
- [ ] 纯解释修订生成新 assessment／report revision，不重跑生信。需新计算时生成关联原候选的 proposed plan，由用户确认后进入执行链。
- [ ] 专家反馈进入待审核案例区，经整理与回归验证后发布新的规则、技能或文献关联；不自动修改线上规则或模型。
- [ ] 将发布记录与引用快照纳入备份；审核追加记录、访问审计和备份共同支持追溯，不将普通数据库表描述为不可篡改存证。

**代码落点：**`analysis_runner.py` 的结果解析和证据附件；`open-webui/backend/open_webui/utils/report_evidence.py`、analysis delivery／internal report 相关模块；后端 models／router 及报告、审核 UI。

**接口变化：**新增候选证据包、AssessmentRevision、ReviewEvent；报告查询支持明确 revision；增加生成研判和提交审核的授权入口。通过后端关联 run 与项目，将裁剪后的只读 evidence bundle 交给 BioAgent，不扩大模型文件访问范围。

**验收场景：**篡改源数值、错误分母、错配候选、伪造论文 ID、版本冲突、相关证据重复、缺失 CheckV／对照、边界阈值、多节段不完整、模型新增事实、重复审核及旧版回看。每条正式研判引用可回到计算记录或适用资料，冲突与缺失完整保留；候选性能以专家冻结集评估。

**迁移与回退：**保留已有 schema v4 数值报告只读展示；新研判采用独立版本对象。停用研判生成或回退模型时，现有分析仍执行；错误报告以新版本更正并标记替代关系，不删除原报告。

## 6. 阶段 4：逐步迁移到本地小模型（含可替换 Harness）

**目标：**在同一任务与证据契约上替换模型供应方和会话运行时，建立本地默认运行，并为后续量化模型微调留下干净数据。**前置条件：**阶段 2／3 在现有模型上有固定评测数据及可追溯基线；推理硬件已盘点。

### 4.1 拆出模型无关边界

- [ ] 在 `runtime.py`、`config.py`、`conversation_context.py` 与 adapter 之间定义最小 provider 接口：输入 task_kind、schema、有限上下文、模型配置、超时；输出结构化动作或研判结果及耗时／错误信息。
- [ ] 将 Claude Agent SDK 会话、resume／transcript 和 MiniMax 配置封装为现有 provider 实现。保留现有对外 chat 及 analysis 接口，不让本地模型适配依赖 Claude session ID。DeepSeek Harness 或其它编排器只增加适配器，不复制 catalog／compiler／runner。
- [ ] 业务上下文由后端历史与确定性摘要构造，现有 SDK transcript 保留作历史审计。新 provider 会话使用独立命名空间，不强行把 SDK transcript 转成可恢复的本地推理状态。
- [ ] 检索、规则、引用验证和工具调度由宿主执行，本地模型首期只需可靠生成 schema 结果，不要求自主调用多轮 MCP 工具。
- [ ] 将结构化输出错误、超时和不可用映射为统一错误。工程初始采用单次生成、严格校验；失败时明确降级，不做无限修复循环。

### 4.2 本地评测、切换与云端边界

- [ ] 根据实际显存／内存、上下文需求、许可、中文表现和结构化输出能力筛选本地模型及推理后端，记录量化方式、模型哈希和推理参数。候选选型是本阶段交付，不预先假设硬件或型号。
- [ ] 按四类任务分别评测：意图／追问、受控参数建议、引用式知识问答、候选证据说明。使用相同资料快照、证据包和 schema 与 MiniMax-M3 比较。
- [ ] 影子运行不注册真实 proposal、不修改报告、不启动工具或计算。模型输出只进入独立评测记录，专家盲审引用适用性和结论保真度。
- [ ] 发布门槛包括严格结构化输出通过率、合法动作率、引用定位及语义正确率、任务完成率、遗漏冲突率、幻觉事实率、首响应与总延迟、人工修订成本。未达到某能力门槛时该能力保持模板／人工路径。
- [ ] 固定负向用例中的越权执行、伪造引用进入正式报告和禁用云端时的外发必须全部被拦截；质量与性能指标在试运行前按基线冻结目标，不以模型自评替代。
- [ ] 切换顺序为意图／追问 → 参数建议 → 引用问答 → 证据说明。按部署或项目配置指定 provider，记录配置变更及模型版本；切换不改变已确认的 execution spec。
- [ ] 默认配置 local_only。另设管理员允许的显式 cloud_enabled 策略，用户对当前任务启用并确认将发送的字段后才调用云端；不发送原始 FASTQ、私有路径或无关临床背景。
- [ ] 本地不可用时保留表单规划、确定性执行及数值报告；没有人工启用云端的授权就显示模型不可用并转专家，不自动回退到远端模型。
- [ ] 定义微调包格式：task_kind、输入证据/检索片段、合格结构化输出、专家修订、模型与知识版本。只收录审核通过样本；发布新模型包前在留出集上重复阶段 4.2 门槛。

**验收：**断开云端可完成已启用的本地任务；禁用知识网络更新时仍能使用本地快照；provider 超时、JSON 无效、上下文过长和本地服务重启不损坏会话或分析状态。不同模型对同一冻结方案产生相同的确定性编译结果。

**迁移与回退：**按能力配置回到已通过验证的本地版本或模板／人工路径。回到 MiniMax-M3 仍必须满足显式云端授权；不能把“回退”当作自动外发的理由。旧输出与模型元数据保留，新模型不重写历史报告。

## 7. 阶段 5：条件接入专项服务与 subagent

**目标：**补充有明确增量价值的专项深度能力。**前置条件：**服务实际可用，项目权限、版本化产物与证据契约已建立；不要求先完成所有本地模型切换。

### 5.1 先判断需要什么组件

| 专项需求                           | 默认实现                              | 采用 subagent 的条件                                     |
| ---------------------------------- | ------------------------------------- | -------------------------------------------------------- |
| 查询 ICTV 分类条目、规则或标志基因 | 本地知识检索；必要时只读 MCP 知识服务 | 单次查询不需要 subagent                                  |
| 执行分类算法、比对或系统发育步骤   | 注册工具／workflow 适配器             | 专业多步决策确需根据中间结果反复选择步骤，且固定策略不足 |
| 多证据汇总与解释                   | 确定性证据服务＋主 Agent              | 首期不新增融合 subagent；后续只有独立评测证明收益才调整  |
| 病毒注释                           | 优先使用已接入的 Workflow 6           | 新服务有现有流程不具备的目标，并有可核验增量结果         |

### 5.2 接入与验收任务

- [ ] 对服务登记 capability_id、版本、健康状态、输入 artifact／候选要求、资源预算、支持任务、输出 schema 与证据格式；未通过验证只在管理端展示。
- [ ] `SpecialistTask` 绑定 project、父 run／candidate、输入快照、服务版本、状态及结果引用。创建前展示任务范围、计算／外发数据及预算，由用户确认。
- [ ] MCP client 由宿主服务持有。将查询工具与会启动计算的工具分别授权；本地模块继续直接调用，SSH worker 不为统一形式而改造为 MCP。
- [ ] 计算型调用使用任务 ID／幂等键，超时后先查询远端状态再决定重试；外部断线不等于失败。缺少幂等或状态查询能力的服务不开放自动重试。
- [ ] subagent 限制工具白名单、上下文、预算、超时和输出位置，只写指定的任务产物；不修改主方案、原始输入或正式报告，不再自行派生其他 agent。
- [ ] 专项结果经过 schema、来源、样本身份与版本验证后才进入原候选证据图；无法验证的结果标为不完整，不直接影响正式结论。
- [ ] UI 采用“追加专项分析”，不用没有可执行内容的 deep 模式或默认勾选的未上线 Agent。

**代码落点：**复用 `taxonagent_adapter.py` 的类型边界；扩展工具目录、宿主服务调用、WebUI 专项任务模型和候选卡。若固定算法即可完成，不为其增加 Agent 运行时。

**验收：**健康检查失败、服务版本改变、超时但远端仍运行、重复确认、证据缺失、候选错配、引用无出处、越权写入和外发禁用均被正确处理；服务的已知输入得到可独立核验输出。

**回退：**关闭能力入口并保留历史任务和证据。已启动的外部任务先核对状态再处理，不随本机配置关闭而盲目重启或终止；基础 Workflow 1–6 和本地知识问答保持可用。

## 8. 验证、上线与维护

### 8.1 按变更选择检查

代码修改后遵循仓库顺序：相关 Python／Vitest 测试 → Ruff → Prettier check → 如涉及前端应用，最后仅一次 build。不要使用产生大量既有类型错误的 `npm run check` 作为验收。

| 变更                             | 优先验证                                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| catalog、参数、compiler、adapter | `agent/tests/test_deterministic_planner.py`、`test_workflow_adapters.py`、`test_deterministic_runtime.py`   |
| 初筛与执行状态                   | `test_adaptive_routing.py`、`test_analysis_runner.py`、`test_remote_worker.py`、`test_remote_client.py`     |
| 对话与 provider                  | `test_conversation_contract.py`、`test_runtime.py`、`test_adapter.py`，随后运行冻结的真实模型评测           |
| 业务权限与版本                   | 后端 `test_analysis_datasets_api`、`test_analysis_plans_api`、`test_analysis`，增加项目／上传／审核行为测试 |
| 交付与证据                       | 后端 `test_report_evidence`、`test_analysis_run_delivery`，补充候选来源与引用错配测试                       |
| 前端行为                         | `analysisRun.test.ts`、analysis API tests，新增对应交互验收                                                 |

Agent 测试从 `agent` 目录运行指定文件，按根 README 使用 adapter 环境及已有 pytest 路径。后端测试从 `open-webui/backend` 运行，采用 README 的测试环境变量。真正执行生信的测试单独登记，所有产物写入 run root。

前端最终 build 从 `open-webui` 执行，完整输出进入 `/tmp`，只检查日志结尾：

```sh
NODE_OPTIONS=--max-old-space-size=8192 npm run build >/tmp/bioagent-frontend-build.log 2>&1
```

本次仅新增静态 HTML 与 Markdown，验收包括格式、链接、章节一致性、浏览器离线展示、窄屏横向滚动和打印，不需要运行应用 build 或生信测试。

### 8.2 上线观察与退出条件

- **执行可靠性：**重复启动数、等待时长、资源等待原因、SSH 状态过期时长、interrupted／恢复成功记录、产物校验失败数。
- **知识与研判：**检索不足率、定位失效数、引用被拒绝数、冲突保留率、专家需补证比例与修订原因；分来源版本统计。
- **模型迁移：**schema 错误、任务成功、延迟、不可用和显式云端调用记录；不把临时用户对话全部作为自动训练数据。
- **报告发布：**来源不可复算、关键引用失效或候选身份错配时停止受影响版本发布；保留运行事实及已有合法报告，创建修订任务。
- **备份恢复：**覆盖业务数据库、发布知识包、运行状态和报告／审核快照；恢复演练验证权限、历史引用与 run 关联。保留策略在真实项目启用前配置。

## 9. 设计依据与维护方式

- [顶层设计 HTML](bioagent-top-level-design.html) 是战略定位、业务目标和组件责任的总览；本文是实施依赖、提示词与验收清单。[建设情况评价](XvirMind_建设情况总结评价_20260910.html) 记录 2026-09-10 的现状，不替代本清单中的未完成任务。模式语义、阶段编号、证据状态、壁垒划分或组件分工改变时，设计文档与本文一起更新。
- 关键词固定为：**本地化、产业化、易迭代更新、本地数据库**。若某项任务只增强通用前端或某一家 Harness 而不同时增强上述之一，默认降优先级或不做。
- [ICTV Code](https://ictv.global/about/code)：分类标准与类群适用性。规则应用需固定来源版本，不把一个百分比推广到所有病毒。
- [CheckV 原始研究](https://www.nature.com/articles/s41587-020-00774-7)：完整度与宿主污染评估。其证据是融合输入的一部分。
- [NCBI BLAST 数据库说明](https://blast.ncbi.nlm.nih.gov/doc/blast-help/blastdatabases.html)：参考序列与派生索引的用途；具体部署版本由阶段 0 盘点。
- [MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)：宿主、客户端和服务端职责；权限、幂等、任务恢复和证据校验仍由本系统实现。

强化学习调度、未经验证的概率融合、自动训练、自动改写线上规则与自主无限派生 Agent 不在本路线内。未来若提出这些需求，先补充独立收益验证及验收标准，再修订设计。
