XvirMind 建设情况总结与评价

项目：宏转录组未知病毒自动鉴定系统（XvirMind / BioAgent）　|　评价日期：2026-09-10　|　口径：对照研究方案与现网代码，不含 Benchmark 专项

一句话结论：项目已经完成从「聊天演示」到「可审计的确定性生信执行器」的关键转向，计算产线和工作流适配是当前最扎实的部分；但对照研究方案中的「AI 协诊专家」，以及团队已达成的战略共识——壁垒在垂直知识库与本地模型、而非前端或通用 Agent 框架——知识层、本地数据库治理、多证据研判和私有化模型仍明显滞后。系统目前更接近「内部可用的固定分析执行器」，距离「可产业化交付的疾控本地化鉴定系统」仍有一整层领域内核没有建起来。

1. 评价口径与材料范围

本次评价只回答「相对原规划，系统现在建成了什么、缺什么、方向是否跑偏」，不把 Benchmark 产品作为建设完成度的一部分。

  • 目标文档：《宏转录组未知病毒自动鉴定系统研究方案：AI 驱动的 Harness 工程与智能决策框架》（v0616，17 页）。目标是从固定产线升级为「专家级综合研判 + 应急智能调度 + 可解释人机互信」。
  • 运行与代码：计算产线 /data/user/guojindan/Projects/Workflows；最新 Agent 实现 /data/user/liufangzhou/projects/bioagent（源码核对 2026-09-09：agent 3ba16a0）；cyclone 部署态 /data/bioagent 仍明显滞后；早期 Harness 原型已归档为 XvirMind_old。
  • 不算完成的标准：「源码里有模块」不等于「真实数据端到端验证通过」，更不等于「可对用户开放」。下文凡写「已实现」，均指代码存在；凡写「已生产可用」，才指部署并跑通。

2. 总体判断：走到了哪一步

研究方案把实施分成五段：阶段 0 基线、阶段 1 推理与调度、阶段 2 可解释报告与专家反馈、阶段 3 自优化闭环、阶段 4 生产验证。若按这个尺子看：

研究方案阶段状态实际落到了哪里
0 基线搭建基本完成双节点拓扑、Open WebUI 演示链路、W1–W6 部署、Dashboard 骨架均已存在。这是目前唯一接近「完成」的阶段。
1 推理引擎与调度器部分完成调度只做成了规则式路径（auto / emergency / standard + 5% Kraken 初筛），没有推理引擎、没有矛盾检测、没有 MCP 调度器，也没有强化学习。
2 可解释报告与专家反馈工程版半完成后端可确定性渲染数值诊断意见书（schema v4），禁止模型写 HTML。没有候选级研判、没有文献引用、没有专家打回。
3 自优化闭环未开始无反馈数据集、无 prompt/规则迭代机制、无本地模型训练闭环。这与当前「先把事实管住」的工程原则一致，但领域壁垒因此还没开始积累。
4 生产验证与交付未开始无私有化部署包、无本地量化模型、无参考库版本目录、无疾控侧交付手册。W9 基因组补齐仍在开发，不在 Agent 主链。

更准确的阶段性描述是：工程上已经越过「让模型自己拼 Snakemake」的危险区，进入「确定性 runner + 类型化 workflow 适配」；业务上仍停在「能选文件、能编译方案、能出流程指标报告」；领域上几乎还没有「知识、本地库、研判、本地模型」这四块壁垒资产。

这个判断不是否定现有工作。把执行权从模型手里收回、用 catalog / compiler / adapter 卡住输入契约，是后续做可信研判和本地小模型的前提。问题在于：这块正确的工程地基已经够用，继续加厚通用 Agent / 前端，边际收益会迅速下降；真正该加厚的是本地数据库、知识发布和研判规则。

3. 分层建设现状

3.1 计算层：最扎实，也最接近产业化

生产流水线在 172.24.195.66 的 Workflows 仓，是当前最可交付的资产。Agent 已为 W1–W6 编写类型化 adapter 与 artifact 契约；W7 为方法学对照，不进主鉴定链。

评价：计算层已经具备「标准流程插件化」的物理基础，但还没有被产品化成「带版本、带清单、带热切换的本地数据库 + 流程插件目录」。缺的不是再写一条 Snakemake，而是参考库发布、校验、回滚和与报告绑定。

3.2 Agent / 执行内核：方向正确，实现超前于部署

最新代码在 liufangzhou 仓，核心已经不是「通用对话 Agent」，而是一套受控编译—执行栈：

  • workflow_catalog.py：公开生物学阶段与 typed artifact，对用户隐藏 Snakemake rule 名。
  • deterministic_planner.py / pipeline_spec.py：依赖闭包、路径、配对、样本一致性由代码决定，不由模型决定。
  • workflow_adapters.py：W1–W6 的复制、物化、config 改写、phase 目标。
  • analysis_runner.py + SSH worker + 私有 tmux + flock：远端串行准入，本机停服务不杀远端任务。
  • adaptive_routing.py：auto / emergency / standard；5% 抽样 + Kraken 门槛。当前 auto 在高置信时仍可能结束整条 pipeline（设计文档已要求改为「快报后继续」）。
  • conversation_contract.py：模型只能 respond / clarify / propose_patch，不能直接启动计算。
  • 报告：Open WebUI 后端按 telemetry 渲染，禁止模型输出可执行 HTML。

同时存在明显的「两套运行态」：cyclone /data/bioagent/agent 仍是早期 adapter / runtime / config 三文件结构，README 还停留在「模型通过 Skill 两次确认后 Bash 调 Snakemake」。评测、演示、开发若走错目录，会看到完全不同的系统。

3.3 交互层：可用骨架，不是竞争力

Open WebUI fork 提供登录、聊天、分析页、Dashboard、System Status。分析页已能做远端文件选择、方案确认、模式切换；Dashboard 项目数组仍是静态示例；大文件上传未闭环；真实项目 / 成员 / 权限未建立。这些对内部试用足够，对疾控私有化不够，也不应再被当成核心建设对象——开源 WebUI 或 DeepSeek Harness 前端都可以替换。

3.4 知识层：最大缺口，也是战略上最不该空着的一层

研究方案把 ICTV 知识、陷阱库、规则层、文献引用写成系统差异点。现状是：

  • 检索契约（Citation / RetrievalAdapter）已定义，但 ConversationAction.validate_action 会清空 citations。
  • TaxonAgent 仅暴露 ictv_family_info，本机默认关闭，首次调用很慢，且不是本地知识快照。
  • XvirMind_old/knowledge 与 knowledge_graph 只是 2026-04 的 YAML/Markdown 占位，不能当知识库。
  • 没有 SQLite 资料包、没有 FTS 索引、没有审核发布流、没有知识版本与报告绑定。

也就是说：系统现在能「算出一些数」，还不能「用本地、可追溯的专业知识解释这些数」。

3.5 模型层：开发期云端模型，生产期本地化未立项

开发链路固定为 Claude Agent SDK → MiniMax-M3。没有 provider 解耦，没有量化本地模型，没有在算力受限条件下的结构化输出评测，更没有用专家反馈做微调的数据管道。疾控私有化部署的核心难点——小显存、量化、断网、结构化动作稳定——目前都还停留在设计文档里。

5. 对照战略共识的偏差

上次讨论已经把竞争力说清楚了。用那四条回看建设，偏差比「功能没做完」更值得重视。

共识建设现实评价
前端和通用 Agent 框架不是壁垒，可替换，甚至可直接接 DeepSeek Harness大量工作仍绑在 Open WebUI fork 与 Claude Agent SDK 上；领域逻辑和会话运行时耦合工程可用，战略危险。应尽快把「对话运行时」收成可替换 provider，而不是继续加深对某一 Harness 的依赖。
真正壁垒是垂直知识库 + 本地模型微调知识只有接口空壳；微调数据管道不存在与共识相反：当前最弱的恰是被认定最该强的。
Agent 与计算服务器分离，用插件 / MCP 接标准流程SSH worker + 复制 workflow 目录已经分离进程，但还不是「标准流程插件目录」；MCP 只用于 TaxonAgent 查询分离这件事做对了。下一步是把 W1–W6 收成带版本的计算插件，而不是让 Agent 进程长在计算节点里。
CDC 私有化：量化本地模型 + 用评测反馈微调未进入实施；默认仍是云端 MiniMax必须先有任务契约和本地知识快照，再谈微调。否则会在错误接口上训练。
交互：选文件 → 自动配对 → 方案 → 报告；标准 / 紧急自适应选文件、预检、模式切换、方案编译已有；自动配对仍不够确定；上传、项目权限、快报后继续未完成主路径轮廓在，离「产业级流水线」差在可靠性和权限，不差在再做一个聊天技能。
多证据研判：计算结果 + 文献 + 知识库；身份、完整性、矛盾检测只有计算结果的数值报告研判产品尚未诞生。工具库和知识图谱如何支撑报告，目前只有设计，没有数据流实现。

做对了、应保留

  • 模型只提案、确定性服务编译和执行。
  • 原始 FASTQ 不搬、不改；产物进独立 run。
  • 计算与交互分节点，本机停服务不杀任务。
  • 报告由模板渲染，杜绝模型编造数字。
  • W1–W6 用 typed artifact 接入，而不是让模型发明 rule。

不该继续加厚的

  • 把 Open WebUI 做成不可替换的产品本体。
  • 在 Claude Agent SDK 上堆更多自主 subagent。
  • 强化学习调度、未校准的总概率融合。
  • 在知识库为空时先做「更聪明的对话」。
  • 把 Dashboard 地图、静态统计当成交付物。

6. 主要风险与建设评价

6.1 风险

  1. 双运行态分裂。最新能力在 liufangzhou，cyclone 部署仍是旧演示链路。对外演示或联调很容易测到过时行为。
  2. 把可替换层当成壁垒。界面和 Harness 继续加深耦合，后续接 DeepSeek Harness 或纯本地 OpenAI 兼容接口会很痛。
  3. 本地数据库不可治理。NT/NR/Kraken/CheckV/rRNA 路径散落在 workflow 配置中，缺少发布清单、哈希、兼容矩阵。私有化交付时无法回答「现场跑的是哪一版库」。
  4. 知识空心化。没有审核过的本地语料，研判模块一旦上马，只能让模型背诵参数或外呼云端，直接打穿 CDC 约束。
  5. 文档领先代码。顶层设计与实施清单已经写到阶段 5，容易造成「规划即完成」的错觉。本次评价把它们视为目标，不视为现状。

6.2 综合评价

若把研究方案终态设为 10 分：

  • 工程执行力 7/10。在「不要让模型碰执行真相」这件事上，团队判断准确，落地也快。
  • 领域壁垒 2/10。垂直知识、本地库、本地模型几乎还没进入建设主航道。
  • 产业化准备 3/10。有分节点和 workflow 源码，没有版本化资产包、权限闭环、离线安装和更新通道。
  • 产品完成度 4/10。内部人员可以走通部分分析；疾控用户不能独立完成「项目—上传—标准/紧急—报告—审核」。

总评：地基选对了，房子还没往该高的地方盖。下一阶段如果仍把精力放在通用 Agent 框架或前端交互上，会与已形成的战略共识相悖。

7. 下一步应把重心放在哪里

建议建设主轴从「把 Agent 做完整」转为「把可本地交付的领域系统做完整」。顺序不是再堆模型能力，而是：

  1. 先同步运行态。以 liufangzhou 的确定性执行栈为唯一实现，对齐 cyclone 部署，避免第三套逻辑。
  2. 把计算产线收成可迭代插件。W1–W6（及以后 W9）以 capability + 参考库快照 + 适配器版本发布；Agent 只通过目录调用，计算节点可独立更新。
  3. 把本地数据库当成一等产品。为 NT/NR/Kraken/CheckV/rRNA 等建立离线发布、校验、切换、回滚；报告绑定库版本。这是私有化的硬条件。
  4. 立即启动知识底座，而不是等业务 CRUD 全部做完。ICTV、工具文档、流程技能、合法文献先做成可审核、可版本化、可断网检索的本地包。
  5. 在数值报告之上补多证据研判。身份鉴定、完整性、矛盾检测必须引用计算证据 + 知识/文献；模型只写受校验的说明。
  6. 把 Harness 降为适配器。Claude SDK、DeepSeek Harness、本地 vLLM/OpenAI 兼容接口走同一 provider；领域规则不进会话框架。
  7. 本地小模型只做四类窄任务。意图、受控改参、带引用问答、证据说明。用冻结任务集和专家修订做评测与后续微调，失败则降级到表单，不自动回云端。
